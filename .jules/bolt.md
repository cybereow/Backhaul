# Bolt's Journal ⚡

Critical, codebase-specific performance learnings only.

## 2026-09-18 - Buffering smux's read side wins nothing at 32KB frames (and the upgrade-handoff trap)
**Learning:** Having buffered the WS read side, I expected the same trick to cut smux's syscalls too - smux collects every frame header with `io.ReadFull(s.conn, hdr[:8])` on an unbuffered conn, which looks exactly like the WS header problem. It does not pay off. Measured with a real smux session over loopback at the default 32KB MaxFrameSize: **2.000 reads/chunk both with and without the 4KB buffer**, and throughput identical (medians 58005 vs 58119 ns/op, ranges fully overlapping). The reason is the size ratio: a 4KB fill serves the 8-byte header plus a slice of payload, then the 32KB payload read drains the buffer and still needs its own direct read - so the read count is unchanged, you just moved bytes through an extra copy. The WS case wins because its *messages* are often smaller than the buffer; smux frames are 8x larger than it. An early 3.6% "regression" reading was pure noise - 3 samples was not enough, 6 showed 0.2%.
**Action:** Buffering only removes a syscall when the buffer can swallow a whole protocol unit; compare buffer size against the frame/message size before assuming a header-read win transfers between layers, and take >=6 benchmark samples on this box before believing a sub-5% delta. Separately, a codebase trap worth remembering: `ws.UpgradeHTTP` returns `(netConn, brw, ...)` and the HTTP read buffer in `brw.Reader` can already hold bytes the client pipelined behind its handshake. Those bytes exist ONLY in that buffer - the raw `netConn` can never see them again. `server/transport/wsmux.go` handed the raw `netConn` to `smux.Client`, silently dropping them and starting the mux session mid-frame; the fix is `conn.NetConn()`, matching what the client side already did. `server/transport/ws.go` was always correct. Whenever `UpgradeHTTP` appears, check that nothing downstream uses the bare netConn.

## 2026-09-18 - wsmux/wssmux do NOT use the WebSocket framing layer, and the WS read side was unbuffered
**Learning:** Two separate findings in the WS family. (1) The transports split into two completely different data planes: **ws/wss** really do frame every byte through `network.WebSocketConn` (`NextReader`/`WriteMessage`) via `WSConnectionHandler`, but **wsmux/wssmux** use the WebSocket handshake only to get through middleboxes and then run smux over the *raw* conn - client side `smux.Server(tunnelConn.NetConn(), ...)`, server side `smux.Client(netConn, ...)` using the raw `netConn` straight from `ws.UpgradeHTTP`, never the `WebSocketConn`. So an optimization to the WS framing layer helps ws/wss and the control channels, and does nothing at all for wsmux/wssmux payload. (2) The WS read side had no buffer: `wsutil.NewReader` read straight off the socket, and `ws.ReadHeader` collects each 2-14 byte frame header with *two* separate `io.ReadFull` calls. Measured at exactly 3 socket reads per message (96 reads for 32 messages), two of them for the header alone - on interactive traffic two thirds of all read syscalls were fetching four bytes of header. Note neither smux nor the WS reader buffers by default; `io.ReadFull(s.conn, hdr[:8])` in smux's recvLoop has the same shape.
**Action:** Before optimizing anything in the WS family, check which data plane it is on - grep for `NetConn()` and `smux.Client|smux.Server` first; `wsmux_*.go` payload work belongs in the smux/handler layer, not `network/websocket.go`. When buffering a conn's read side here, the buffer must be shared by *every* read path (`NextReader`, `ReadMessage`, and the conn returned by `NetConn`), because `client/transport/ws.go` reads a leg with `ReadMessage` and then hands the same conn to `WSConnectionHandler`, which reads it with `NextReader` - separate buffers would silently strand bytes between them. Keep the buffer well under `handlers.copyBufferSize` (64KB) so `bufio`'s empty-buffer direct-read path still lands large payloads straight in the copy buffer instead of copying twice; 4KB measured best, 16KB cut syscalls further on 8KB messages but cost more per-connection memory and lost the gain to the extra memcpy. Also: the one remaining alloc/op is `make([]byte, 2, 12)` inside gobwas's `ReadHeader` - not fixable without forking the library.

## 2026-09-18 - `time.After` in the UDP pumps' select loop parks a 60s timer per packet
**Learning:** Every UDP forwarding loop (`udpToTCP` in accept_udp.go, `udpLocalCopy`/`udpTunnelCopy` in udp.go) used `case <-time.After(inactivityTimeout)` as the idle arm of a `for { select }`. That is not a one-off cost: each loop turn allocates a Timer + channel AND parks the timer in the runtime timer heap for the full 60s, even though the select abandons it as soon as the next packet lands. Steady state is ~60 x packets-per-sec live dead timers (600k at 10k pps) - resident memory plus an inflated timer heap that every other deadline in the process (including netpoll read/write deadlines on every other connection) then sifts past. `time.After` accounted for 62% of allocated objects in the pump. The same loops also paid for disabled logging: variadic log args are boxed into an `[]any` before the call, and `addr.String()` formats a fresh IP:port string, so an unguarded `Tracef`/`Debugf` allocates per packet at the default level. Combined with a per-packet `append(header, data...)` (header's cap is exactly 2, so append always grows), the pump cost 840 B and 6 allocs to forward a 512-byte packet.
**Action:** In this codebase, treat `time.After` inside any `for { select }` as a bug, not a style nit - hoist one `time.NewTimer` and re-arm it with stop-drain-Reset. Grep `time.After(` under internal/ before assuming a loop is clean; the striping package already does this right, the UDP plane did not. Guard per-packet `Tracef`/`Debugf` with `IsLevelEnabled`, and never build a frame with `append` onto a tightly-sized header. Result: 674 -> 300 ns/op, 840 B -> 0 B, 6 -> 0 allocs/op. Watch out when testing this: dropping the `Reset` does not make the pump time out early, it makes it hang forever, because the drain step swallows the one and only fire - so an idle-path regression test must assert both "does not exit while packets flow" and "does exit once quiet".

## 2026-09-16 - Striping Read's stall timer must live on the Conn, not be Read-local
**Learning:** `Conn.Read`'s blocking loop created a fresh `time.NewTimer(stallTimeout)` every turn — the last remaining per-chunk allocation on the reassembly hot path (3 allocs/op in BenchmarkConnRead, after the read pool had already killed the payload allocs). First fix attempt made a Read-*local* reusable timer with `defer timer.Stop()`; it got *worse* (3→4 allocs, slower). Two traps: (1) BenchmarkConnRead is single-leg in-order, so each Read blocks exactly one loop turn — a Read-local timer is still allocated once per Read, no reuse ever shows; (2) `defer timer.Stop()` is a method value that itself heap-allocates. The win only lands when the timer persists *across* Read calls.
**Action:** Put the reusable timer on the Conn (`readTimer`), guarded by `rmu` (Read holds it for its whole duration), lazily created, re-armed with the Stop-drain-Reset idiom each turn. Result: 3→0 allocs/op, ~7.8→9.4 GB/s. When reusing a timer to kill allocs, check whether the alloc-measuring benchmark actually exercises multi-turn reuse, and never reach for `defer x.Stop()` in the hot loop — it allocates.

## 2026-09-14 - Striping data plane: read path was the un-pooled mirror of the write path
**Learning:** `internal/utils/striping` is the throughput-critical data plane (one flow split across N legs). The write path already pools chunk buffers (`chunkPool`, commit 187933e), but the read/reassembly path in `readLeg` still did `make([]byte, length)` per inbound chunk — one 16KB allocation per chunk on every striped download. The two sides are symmetric; whenever one gets a buffer-pool optimization, check the other.
**Action:** Pooling the read side is safe *only* because `readBuf` is replaced solely when empty (every assignment site is guarded by `len(readBuf)==0`), so a buffer can be returned to the pool exactly once, right after the final `copy` drains it. Track the backing `*[]byte` on the `chunk` and on a `readBufBase` field; never return a buffer still referenced by `pending` or an in-flight `readBuf`.

## 2026-09-14 - Benchmarking the striping Read path: never feed it with net.Pipe
**Learning:** A `BenchmarkConnRead` fed via `net.Pipe` stalls — the synchronous, unbuffered pipe couples every peer `Write` to the reader's `ReadFull`s and intermittently deadlocks long enough to trip the 20s `stallTimeout`, giving a flaky ~20s/op result.
**Action:** Feed the read benchmark from a non-blocking in-memory `net.Conn` whose `Read` serves an endless framed stream from one reused buffer (see `read_alloc_test.go`'s `seqFrameConn`). Deterministic, fast (~7 GB/s), and measures the Conn's own reassembly/allocation cost, not the pipe's.
